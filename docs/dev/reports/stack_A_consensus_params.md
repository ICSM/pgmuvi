**The mini-stack #156-#162 is not a real decomposition.**
- pr1 (+67 code) and pr2 (+333) are honest small steps. pr3 is +1,586 and pr4 is +1,992 (all in `lightcurve.py`).
- None of pr2-pr4 contains its predecessor's tip.
- `pr5-consensus-diagnostics-schema` is essentially the whole giant PR: +13.5k/−3.1k in `lightcurve.py`, including all of fit-history/provenance, with none of that feature's tests (`tests/test_fit_history.py` exists only in the giant PR).
- pr6 (upload validation) and pr7 (regression tests) each sit on pr5.

Conclusion: ignore the mini-stack boundaries. Treat `integration-consensus-test` as the reference implementation of consensus.

**Scaffolding density is high.**
- **Parameter stack, test-to-code ratio about 2:1.** About 20 of its 29 PRs change fewer than 60 lines of code. Examples: pr8 has 8 code lines and 50 test lines; pr17 has 0 and 50; pr24 has 1 and 47; pr27 and pr28 each add 20-30 code lines and no tests. Many are "skip-reason / summary-reason / specific-reason / report" iterations on one dict.
- **Unused enum members.** `ParameterSpec` enums declare strategies that nothing implements: `LS_PERIOD`, `ACF_PERIOD`, `FLUX_STD`, `MAD`, `CADENCE`, `BASELINE` and `VARIABILITY_TIMESCALE` have zero references at the tip.
- **Consensus bookkeeping.** About 2,000 lines of the consensus code are `_consensus_*` bookkeeping/validation methods. `_consensus_validate_result_structure` alone is 973 lines. Another ~430 lines are module-level `_CONSENSUS_*` schema/status constants.

## C. Conflicts and contradictions

1. **Junk files committed then removed.**
   - `pr34` adds `debug1.txt`, `debug2.txt` and `debug3.txt` (1,118 lines); `pr35` deletes them.
   - `pr35` adds `tests/test_constraint_integrity_regression.py.orig`.
   - `pr36` adds `pgmuvi/lightcurve.py.orig` (22,255 lines). It is still present at pr55 and is removed somewhere in the pr59→pr98 range.
   - The integration branch deletes `pgmuvi/test_script.py`.
2. **SM schema constraints flip-flop.**
   - `pr30` sets `mixture_scales`/`mixture_weights` `initial_value=None`, `constraint_strategy=None`, and tightens the caps to 1e3/1e4 ("avoid overriding SM defaults").
   - `pr33` restores `ConstraintStrategy.DEFAULT` but with intersect semantics.
   - `pr51` then widens those caps from flux diagnostics, because the caps the workflow introduced pinned bright data.
   - pr30, pr33, pr35 and pr51 mostly fix problems that the parameter workflow itself created.
3. **Transform inheritance.** `pr37` makes filtered and per-band LCs inherit the parent `xtransform`/`ytransform`. `pr129` reverts this for consensus band LCs (`xtransform=None, ytransform=None, center_time=False`), because a 2D affine transform cannot apply to 1D band times.
4. **Duplicated commit and broken ancestry.** `pr38`'s `learn_additional_noise` commit (69706d6) is re-applied as 397e503 in `pr39`, and pr39 does not descend from pr38. `pr16` likewise does not descend from pr15. `pr172` is based on `pr169`, not `pr171`.
5. **Defaults flip.** `learn_additional_noise` defaults to `False` (pr38), then `None` (on) in pr173. `duplicate_wavelength_policy` defaults to `"first"` (pr166), then `"error"` (pr172). The docs written in between (pr99 consensus how-to) describe the old defaults until pr173 patches them.
6. **Consensus vs parameter workflow implement the same thing twice.**
   - Consensus SM initialisation (`_consensus_build_guess`, `_consensus_build_spectral_mixture_initialization`, `_consensus_build_multicomponent_initialization`) duplicates the builder's `GuessStrategy.CONSENSUS_FREQUENCY` / `CONSENSUS_MULTICOMP_PERIOD` (`_estimate_consensus_frequency`, `_estimate_consensus_multicomp_period`, `_estimate_frequency_fallback`).
   - Consensus applies its own `Interval`s through `set_constraint` and sets `__CONTRAINTS_SET`. The workflow (on by default) then applied DEFAULT schema constraints over them, so `pr34` had to add "preserve consensus constraints through inner fits" and re-validation (`_consensus_get_registered_sm_constraint_bounds`).
   - The pass-through `# use_parameter_workflow=use_parameter_workflow,` is commented out in the consensus dispatch, so whether the workflow runs inside consensus fits is implicit.
7. **Three overlapping sources of initial values and bounds** in `_fit_core`: `set_default_constraints` (main), then `_apply_parameter_workflow_estimates` (schema), then the MLS/best-band/`guess` `set_hypers`, with `initialization.py` also used inside `set_model`. `spectral_mixture_ard.py` (pr124) adds a fourth for 2D SM. Any replacement should pick one.
8. **The consensus mini-stack vs the giant PR.** PR descriptions say pr5 is "diagnostics schema", but it carries fit-history/provenance (about 2.3k lines) whose tests are only in #154. pr4's "frequency-space refactor" is re-done inside pr5.

## D. `lightcurve.py` growth in this theme

From an AST diff of main against the tip (methods only):
- **13.4k lines of new functions/methods** on `Lightcurve` and its helpers, plus ~440 module-level constant lines, minus a 406-line `fit` (moved into `_fit_core`).
- **This theme accounts for roughly 12k of that:**
  - consensus ~8.2k (of which ~2.0k is validation/status bookkeeping and ~0.43k schema constants)
  - fit history/configuration/provenance ~2.3k
  - duplicate-wavelength channels ~0.6k
  - transforms (`Shift`, `TimeCenter`, uncertainty transforms) ~0.3k
  - parameter-workflow hooks/reporting ~0.35k
  - likelihood/dtype plumbing ~0.3k
- The wavelength-advisory wrappers (~0.65k) are another theme.

**How much is genuinely a `Lightcurve` method?**
- Very little. The public surface that users would call is `fit(fit_strategy=...)` (or a `fit_consensus`), `consensus_diagnostics`, the `center_time` constructor kwarg, `learn_additional_noise`, and `transform_y_uncertainty`. That is well under 1k lines.
- **Should be standalone modules taking arrays:**
  - **consensus science** (band candidates, robust aggregation, clustering, LS-ACF harmonic check, frequency↔period bound conversion): ~1.5k after slimming, in `pgmuvi/consensus.py`
  - **transformer classes:** they already live at the top of `lightcurve.py`; move them to `pgmuvi/transforms.py`
  - **duplicate-channel resolution:** `pgmuvi/preprocess/channels.py`
  - **constraint helpers:** already moved to `constraint_utils.py`
- **Should be deleted:** the result-schema validation, the status/rejection machinery, the fit-history/provenance/reproducibility code and `FitFailureSummary`. That is roughly 5k lines of the ~12k.

## E. Proposed replacement stack

Each PR is under ~800 code lines and stands alone against main. Fix PRs come first, so they can merge independently of the consensus decision.

1. **Fix transforms and uncertainties** (B1-B4): `transform_uncertainty`/`transform_variance`, the `transform_y` bug, `transform_x` coercion in prediction/plot paths, and transform inheritance in `filter_*`. ~150 code + ~200 tests. *Source:* pr114 (lightcurve part), pr37 hunks.
2. **float64 default dtype** (B6). ~50 + 80. *Source:* pr36, pr110.
